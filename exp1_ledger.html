§1 · The experiment

Two stages: replay, then recovery

E1 — sequential replay. Four harnesses — four reasoning structures, not four repos — forecast the same two questions on five dates in chronological order. Each day a harness sees its own previous forecasts and, where its shape has one, its own memory or belief block from yesterday. All four read the same date-gated corpus through the same search tool.

E2 — program recovery. For every forecast produced, an extractor model reads that day's trajectory and writes down the quantities the reasoning used, as name = value. Those per-day tables are reconciled into one canonical schema, and then one literal-free program is synthesised per harness×question that must reproduce every forecast that harness made from its variables alone.

Why this is not chain-of-thought, for any of the four. CoT is a transcript — free text read once and thrown away. Here the trajectory is raw material for an executable object: a program with named inputs, fitted jointly across every instance, that can be re-run, perturbed, and diffed. The recovered code is the DSL instance; the trajectory is just where it was mined from. And the recovery is per-harness: the analytica harness's staged decompose→ground→synthesise structure should compress into a program easily; whether react's free-form loop does is precisely one of the measurements.

§3 · Data

The corpus, the gate, and the one deviation from the paper

Provenance. The articles are the real FutureSim corpus — Hugging Face dataset shash42/forecast-news, the CCNews-derived, deduplicated, dated tree the paper uses. We pulled the parquet shards for 2025-12 through 2026-03: 120 day-directories, 412 MB, indexed into 339,801 rows spanning 2025-12-01 → 2026-03-31. Questions come from nikhilchandak/OpenForesight, split aljazeera2026Q1 — the exact 330-question set the FutureSim paper evaluates on.

The gate. At simulation date D, an agent can see only articles with date ≤ D, enforced in the SQL of the search tool itself — there is no code path that returns a later article, regardless of what the model asks for. The indexed date field is the corpus's crawl date (the day the article entered CCNews), which is the conservative choice: an article becomes visible on the day it appeared, never earlier. Verified by hand: querying “March ECB meeting outcome” as-of Jan 20 returns only pre-Jan-20 items.

The deviation, stated plainly. FutureSim's own search tool is hybrid semantic+keyword over a prebuilt LanceDB index — which is 48 GB (measured on the HF repo before deciding). We built a local SQLite FTS5 BM25 index over the same articles instead. Retrieval is therefore weaker than the paper's. It is also byte-identical across all four harnesses, so it is a constant of the experiment, not a confound in it: the comparison is between reasoning structures under fixed retrieval, and no cross-harness conclusion is affected. Absolute forecast quality, however, is a lower bound relative to the paper's setup — that caveat travels with any accuracy number.

The original OpenForesight question is short-answer (“which country will win?”); we binarised it into two yes/no propositions because the belief-dynamics measurements are defined on probabilities of propositions.

Correction — the original control logic was wrong, and the review caught it (F1, fatal). This page first claimed that under one evidence stream “one belief should climb and the other should fall,” scoring separation = netΔ(USA) − netΔ(CAN) as the evidence-tracking signal. The reviewer checked the corpus: both teams won their semifinals on 2026-02-20 — the last simulation date — and the final resolved on 02-22, after the window. Inside the window the evidence never discriminates the two finalists, so a correct forecaster raises both beliefs toward ~0.5 as every other team is eliminated; large separation would mean misreading the news. The metric would have punished exactly the behaviour it should reward. Replaced with: semi-rise (did both beliefs rise across the semifinal date), sum@last (P(USA)+P(CAN) should approach 1 by 02-20 and never exceed it), and complement-coherence error. The pair remains a genuine control — but for coherence under shared evidence, not for direction.

Dates: 2026-01-14, 01-28, 02-08, 02-15, 02-20 — two pre-tournament (rosters, warm-ups), three inside it (group stage, playoffs, eve of the final), so evidence concentrates sharply across the last three and a belief that tracks it has to accelerate.

Scale-up set (Sep 08): four more OpenForesight questions with ≥5-week spans — IQAir most-polluted city, Newcastle/Carrick first defeat, Nepal PM swearing-in, SA T20 captaincy — all resolving YES per the dataset (disclosed; they power the recovery statistics, not directional claims). Runs live in results/exp2.

Why not more questions on day one: the 3-hour budget buys either breadth or sequential depth. Dynamics is the object, and the trajectory is the measurement, so depth won: 2 questions × 4 harnesses × 2 samples × 5 sequential days = 80 forecast-turns, each with a full extractable trace. Statistical claims at n=2 questions are explicitly out of scope; this run establishes the instrument and the effect directions, not population statistics.

§6 · Harnesses

How the four were built, and exactly what each says

The build decision. The four harnesses are four system prompts over one shared substrate — same model, same tool, same loop mechanics, same sequential protocol — not four installed repositories. This was deliberate, twice over. Practically: Analytica's repo needs FMP/FRED/Exa/Wolfram/Kalshi keys and FutureSim's full harness needs the 48 GB index. Scientifically, and more importantly: four repos differ in model calls, retries, context policies, caching, and a hundred engineering choices — a comparison between them is a comparison of repos. Holding the substrate fixed makes reasoning structure the only manipulated variable. The cost, stated honestly: these are faithful re-implementations of each paper's reasoning shape, not the papers' own code, and claims transfer to the originals only insofar as the shape is what matters — which is exactly the hypothesis under test.

What is identical across all four (verbatim, the shared preamble of every system prompt):

You are forecasting a real future event.

The current simulation date is {date}. You know nothing about events after
this date. Use search_news to gather evidence; it can only return articles
published on or before {date}.

Write your reasoning out explicitly as you go -- state the quantities you are
weighing and the numbers you assign them. Someone will later have to
reconstruct exactly how you arrived at your number.

End your final message with a line of exactly this form:
FORECAST: <probability between 0 and 1>

The “write your reasoning out explicitly” instruction is shared by all four, so the observer effect it introduces (verbalising numbers may itself change the forecast) is a constant, not a differential. §7 · Recovery

From trajectory to program: the three steps and the wall around them

Step 1 — the variable table, per turn. The extractor reads one day's searches and reasoning and writes snake_case_name = number, one per line: base rates, sub-probabilities, weights, adjustments, thresholds, counts. The rules that matter: names must describe quantities, never dates or runs; implied numbers (“roughly halves the odds”) are recorded as what they imply (0.5); and it is forbidden to record the final forecast — it records the inputs to the reasoning, never its output. Belt and braces: any declared variable numerically equal to that turn's forecast is dropped mechanically in code, whatever it is named.

Step 2 — reconciliation, per harness×question. Independent extraction gives each day its own names for the same quantities. Step 2 merges them into one canonical schema (5–14 names) and binds every instance to every name — where a quantity was absent from a day's reasoning, the value that reasoning implicitly treated it as. This schema is the discovered coordinate system: the belief trajectory lives in it.

Step 3 — one program. The extractor writes a single def forecast(): that must reproduce every instance's output from its bindings. It sees the schema, all instances' bindings-and-targets, and an excerpt of the original reasoning with the instruction to mirror its shape (“if it set a base rate and applied adjustments, your program sets a base rate and applies adjustments — do not write a curve fit that happens to land on the numbers”). A repair loop feeds back validator violations and the worst-fitting instances, up to 4 attempts.

The program space, in full

# structure
exactly one   def forecast():   with zero arguments; names resolve from an
injected namespace. No other def, no lambda, no class, no import.
forecast() may call itself → recursion available. while available.

# THE rule
NO LITERALS ANYWHERE IN THE BODY. Not 2, not 1, not 0.5, not "".
Every value must arrive as a declared variable or a named constant.

# allowed statements
assignment · augmented assignment · if/elif/else · while · break · continue · return

# banned outright (AST node whitelist, not regex)
for · try · with · comprehensions · generators · attribute access (a.b) ·
subscripting (a[b]) · tuples/lists/dicts/sets · f-strings · lambda · import ·
global/nonlocal · yield · starred · slices

# callable globals (the only calls allowed, by bare name)
min max abs round exp log sqrt clamp logistic noisy_or odds prob

# named constants (so the body never needs a numeral)
ZERO ONE TWO HALF TENTH HUNDREDTH EPS E PI

# execution
exec with __builtins__ = {} plus only the globals above and the bindings;
per-line trace counter, 200,000-step budget → an infinite loop is a failed
fit, not a hung experiment. Return value must be a number.

The validator was exercised before anything ran. A well-formed program (base + noisy-OR pull + while-decay + clamp) passes and executes; the deliberate counterexamples are all caught with line-level messages:

line 4: no-functions -- helper function 'helper' -- the program is a single function
line 3: magic-number -- literal 2 -- declare it as a variable in step 1
line 3: magic-number -- literal 0.7 -- declare it as a variable in step 1
line 3: banned-construct -- Import is not in the program space
line 4: banned-construct -- Attribute is not in the program space
line 2: undeclared -- 'unknown_name' is used but was never declared in step 1
The degeneracy problem — the one way this whole design can lie. The literal ban stops numbers hiding in the program body. It does not stop step 1 declaring final_answer = 0.62 and step 3 writing return final_answer: a perfect fit that measures nothing. Four mechanical defences: (1) step 1's output ban; (2) the in-code drop of any variable equal to the target; (3) a bare return <name> body, or any program with fewer than 3 operations, is rejected outright and re-requested; (4) a degeneracy report computes the strongest single-variable correlation with the target across instances and flags near-passthrough programs (|corr| > 0.98 over ≥6 instances with <5 ops) as suspect. A perfect fit with high degeneracy is recorded as a failed extraction, never as a result. Residual gap, admitted: a near-copy (forecast 0.21, variable 0.2) passes the equality drop; the correlation flag is the net under it, and spot-checking step-1 tables against their traces is the manual audit for what slips both.

Post-review hardening (F2, fatal — see §9): the review proved the no-literal rule was syntactically enforced but semantically bypassable (TENTH*(TWO+TWO+TWO) = 0.6; True+True = 2; an if-chain keyed on any varying variable is a per-instance lookup table). Now: boolean constants are banned, a constant-construction detector rejects any expression built solely from named constants, a branch-count check flags lookup-table programs (branches ≥ n−1), the near-target drop is a tolerance band with a previous-day-forecast exemption — and, because no static defence can prove structure, the gate that actually decides is out-of-sample fit: the program is synthesised again on sample 0's instances alone and evaluated untouched on sample 1's. In-sample fits are reported as descriptive only.

The fit gate (all three required): MAE ≤ 0.02, and ≥80% of instances individually within tolerance, and zero failed executions. MAE alone was the original gate; it passed a program that averaged well while most instances missed, so the per-instance clause was added and the original gate is documented here as a corrected mistake.

What this has to do with Analytica. Nothing is elicited from the Analytica repo and no tree schema is imposed. The DSL instance is recovered: the harness reasons however its shape dictates, and the program+schema are mined from the trace afterwards. For the analytica harness the recovered program should look like its stated synthesis (weights over sub-propositions — effectively its tree, flattened into code); for bayesian, like an odds-update chain; whether react compresses into a program at all is one of the findings, not an assumption.

§9 · Independent review

Adversarial review of the full setup

A reviewer with no stake in the design was pointed at the entire codebase with instructions to be ruthless: leakage paths, validator loopholes (including constructing programs that smuggle constants past the no-literal rule), statistical validity, extraction circularity, harness comparability, orchestration bugs, reproducibility. It read every file, ran its own exploits against the validator and parser, inspected the corpus database and the discarded run, and verified the live process's actual flags. Verdict: 2 fatal, 7 serious, 6 moderate findings, a cluster of minors — and a verified-sound list. Every finding is below with its disposition; every fix was re-verified against the reviewer's own exploit cases before E2 was allowed to run.

F1 fatal
The planned headline metric punished correct forecasting. “Separation” assumed one belief should rise and the other fall — but the reviewer checked the corpus: both teams won their semifinals on 02-20 (the last simulated date) and the final resolved 02-22, outside the window. A correct forecaster raises both beliefs; high separation would mean misreading the news. FIXED. Metric replaced with semi-rise, sum@last coherence (P(USA)+P(CAN) → ~1, never above), and complement error; the original claim is retracted in §4, visibly. Caught before a single conclusion was written.
F2 fatal*
The no-literal rule was semantically empty. Reviewer-built exploits all passed the old validator: TENTH*(TWO+TWO+TWO)+HUNDREDTH*TWO = 0.62; True+True = 2; (EPS<ONE)+(EPS<ONE) = 2; an if-chain over any varying variable is a per-instance lookup table — and the repair loop, by showing failing instances with their targets, actively coaches the synthesiser toward it. Dead code (+ZERO*(a+b)) lifted the op-count past the degeneracy flag. (*fatal for the interpretation “low MAE ⇒ the reasoning was program-like”.) FIXED / MITIGATED. Bool constants banned; constant-construction detector rejects any expression whose every leaf is a named constant (all four exploits now REJECT — re-verified); branch-count flag for lookup tables (branches ≥ n−1). And the honest gate the reviewer demanded: out-of-sample holdout — synthesise on sample 0 alone, evaluate untouched on sample 1, reported per group. In-sample fit is demoted to descriptive. Dead-code padding remains possible in principle; OOS is the backstop.
F3 serious
One bad program would have killed all of E2. A synthesised program binding a name on only one branch raises UnboundLocalError — not in fit_error's except tuple — and the report was written only at the very end, so one crash discarded every already-paid-for group. E2 was set to launch itself unattended. FIXED before E2 ran: NameError caught as a failed fit (verified), per-group try/except, incremental report writes after every group.
F4 serious
Race: the auto-chained E2 watcher fired on file creation, while E1 was still writing its 16 JSON lines — a truncated read or silent partial load. FIXED. Watcher killed minutes before E1 landed; E1 now streams each run to a .tmp (a crash at 15/16 no longer loses everything — also F13) and renames atomically; E2 was launched manually on patched code.
F5 serious
The forecast parser could fabricate certainty. “FORECAST: 85%” clamped to 1.0; the bare-number fallback could turn a list item “1.” into a forecast of 1.0; “0,45” parsed as 0.0. FIXED + RETRO-VERIFIED. Percent divides by 100, comma is a decimal separator, out-of-range is a parse failure that triggers the existing retry, fallback deleted. The strict parser re-run over all 80 collected turns reproduces every stored forecast identically — the bugs were latent, never realised, so the E1 data stands.
F6 serious
Step 2 silently zero-filled mis-copied instance keys and destroyed the audit trail. One key the extractor failed to reproduce verbatim → all-zero bindings, indistinguishable from “the structure changed”; pre-reconcile bindings were overwritten in place, so step 1's actual output was unrecoverable — which also blocked auditing the contamination path (F14). FIXED. Missing keys retried once, still-missing instances excluded loudly (never zero-filled); raw step-1 bindings preserved on every instance and saved in the report; non-numeric values coerce with a logged count instead of crashing the stage.
F7 serious
The target-drop defence both leaked and backfired. Exact-equality dropping let near-copies through (posterior_before_rounding=0.205 vs forecast 0.21) — while for a harness that didn't move, yesterday's forecast equals today's and was dropped: the anchored harnesses lost their most legitimate variable, biasing fit quality against exactly the harnesses whose anchoring the experiment studies. FIXED. Tolerance band (±0.005) with an exemption for values equal to the previous day's forecast; every drop logged by name.
F8 serious
The shared tool budget binds the harnesses unequally. In the discarded run, analytica averaged 8.0 searches/turn (its prompt mandates per-sub-proposition grounding) vs react's 5.0 — so with 5 tool rounds, analytica hits the forced “stop searching” cutoff more often, and analytica-vs-react differences are partly “who got truncated”. The forced stop wasn't even logged. PARTIALLY ADDRESSED. Forced-stop is now recorded per turn as a covariate. It is absent from the already-collected E1 (disclosed limitation of this run); per-call budgeting is deferred to the next run.
F9 serious
n = 1 question pair, 2 samples: no between-harness ranking survives. Sample-to-sample spread is the same magnitude as harness differences. Also, nets computed over whichever dates happened to parse span different windows per run — not comparable. ACCEPTED + FIXED in analysis. Nets now restricted to runs holding both endpoint dates; scope language hardened everywhere: this run establishes the instrument and effect directions. No harness ranking will be claimed from it.
F10 moderate
Reproducibility record was empty, and a default was a trap. No output recorded model, flags or tolerances; the CLI default was --model gpt-5 while the documented runs use gpt-5-mini — a naive rerun would use a different, contamination-riskier model; the step-3 excerpt came from whichever run finished first (nondeterministic). FIXED. Config JSON (all flags + timestamp + corpus span) written next to every output; default corrected to gpt-5-mini; excerpt choice deterministic (lowest sample).
F11 moderate
Prose overstated the gate. Docs said the program “reproduces every forecast”; the actual gate is MAE ≤ 0.02 and ≥80% of instances within tolerance and zero failed executions. FIXED in prose — the gate is stated as the gate, here and in the repo docs.
F12 moderate
react was mislabelled “no memory”. All four harnesses carry their own forecast history, deliberately; react is the history-anchored structural floor, and react-vs-futuresim contrasts “history” with “history + memo”. FIXED in description (§6). The uniform history is by design — it is the anchoring pressure applied equally — and now says so.
F13–F14
Robustness & tool edge cases. E1 held all results in RAM until the end (a crash at 15/16 loses ~90 min of paid calls) and a partial jsonl was silent; a model-passed k=-1 became SQL LIMIT -1 = unlimited dump; the tool description promised “max 10” while code caps at 6; index failures returned “no articles” silently. FIXED. Streaming writes + loud partial warning; k clamped ≥1 at both layers; description aligned; search failures logged to stderr.
F15 moderate
Extractor contamination is real but bounded. gpt-5.2 knows the tournament's outcome. The reviewer traced the bound: step 2 never sees the targets (verified), and step 3's objective is the harness's forecasts, not the truth — so the leak can tint step-1 values and variable naming, not the fit targets. It can matter for the “which variables moved” narrative. ACCEPTED + DISCLOSED. The transcribe-only instruction is the first mitigation; the now-preserved raw step-1 bindings (F6 fix) are the audit trail for spot-checking extracted values against the trace text.
minors
Docstrings in synthesised programs were flagged as magic-strings (repair-loop noise); thread-local DB connections never closed; the analyzer counted step-2 zero-fills as “held fixed”; the step-limiter is per-thread (sound today, fragile if refactored); the API key is visible in the local process command line. Dispositions: docstring whitelisted · connection leak accepted at this scale · zero-fill moot (exclusion replaced it) · comment added · key rotation is on the user — flagged twice now.

What the review verified as sound

  • The date gate holds. All 339,801 rows carry uniform YYYY-MM-DD dates, the gate is in SQL not in a prompt, from_date cannot widen it, and spot-checks of mid-February articles found no post-dated content. The truth labels were verified against the corpus itself (USA beat Canada in overtime, 02-22 — outside the window).
  • The live run is what the docs say it is — gpt-5-mini, effort medium, 5 tool rounds, verified from the process table, not from the docs.
  • The thread-safety fix is real, the corruption class cannot recur, and the discarded run cannot contaminate the clean one (separate directories, verified).
  • The execution sandbox held. With attributes, subscripts and imports banned and __builtins__ empty, the reviewer found no escape; the step-limiter terminates while True.
  • Step 2 never sees the forecasts — the circularity vector is step-1 near-copies only, which is what F7 closes.
  • Carry blocks work: memory/belief extraction succeeded on every non-errored turn, and carry persists across a failed day rather than being wiped.
§9b · The standing audit (scripts/audit_exp1.py). Re-runnable against any results directory: the full exploit battery must REJECT (11/11, incl. number-spelling names, x/x, dead-code padding), every stored forecast must re-parse from its own text (80/80 and 160/160), every logged search is re-executed with its turn's date (483 + 949 replays, zero articles past the gate), every stored program must re-execute to its reported MAE, and every variable table is scanned for answer-copies under the transform battery — a copy counts only if it tracks the answer on ≥80% of instances (one coincidence cannot carry a 10-instance fit), with yesterday's forecast exempt and near-constant-target groups marked ill-posed rather than flagged. Result across both experiment sets: one systematic copy found in 320 variable tables (posterior_odds, odds-form, 10/10) — referenced by no program. Verdict: all fits clean.

Each harness was continued from its real end-state to a probe day with search disabled and one injected role-based news item (goalie out / top centre out / placebo). The one-line finding. Method stability and evidence-tracking anticorrelate across all four harnesses — and the probe localises where each harness's rigidity or plasticity lives: in the searching (futuresim), in the update rule's asymmetry (bayesian), outside the recoverable structure entirely (react), or in daily rewrites of the structure itself (analytica).
§11 · Reproduce

The whole thing, from an empty directory

# data: real FutureSim corpus slice + questions (~400 MB, once)
python scripts/fetch_corpus.py --start 2025-12 --end 2026-03
python scripts/build_index.py                    # ~2 min → data/news.db

# E1: 2 questions x 4 harnesses x 2 samples x 5 sequential dates
export OPENAI_API_KEY=...
python scripts/run_exp1.py --stage e1 --model gpt-5-mini --effort medium \
       --samples 2 --tool-rounds 5 --workers 8 --out results/exp1

# E2: variable extraction + program synthesis per harness x question
python scripts/run_exp1.py --stage e2 --extractor gpt-5.2 --out results/exp1

# measurements: coherence, movement, fit table, programs, trajectories
python scripts/analyze_exp1.py results/exp1

# the standing audit (exploit battery, parser + fit reproduction, date-gate replay)
python scripts/audit_exp1.py results/exp1

# belief dynamics: trajectories, residual drift, sensitivity, distances (+ --temporal)
python scripts/beliefdyn.py results/exp1 --temporal

# the rigidity probe + multi-coordinate rule-compliance
python scripts/run_probe.py --out results/exp1
python scripts/probe_rule_check.py --out results/exp1

Outputs: results/exp1/e1_runs.jsonl — every turn with its searches (queries + returned titles), full reasoning text, carry blocks, forecast, and any error; results/exp1/e2_programs.json — per harness×question the schema, the program, per-instance residuals, degeneracy report, repair history, and the variable trajectory across dates. Analysis re-runs from these files alone, with no API calls.
